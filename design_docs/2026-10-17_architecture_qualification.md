## IMG-GPU gate and its first finding (2026-10-20)

Gate: [`genet-render-host/tests/image_gpu.rs`](../components/genet-render-host/tests/image_gpu.rs), `#[ignore = "... coordinator executes serialized GPU gate"]`, hard failure without an adapter, on branch `img-gpu` (not merged). It decodes real PNGs through `LiveryDocument`, translates the paint list, rasterizes on the one `RenderCore` device and reads the pixels back, against computed expectations (opaque and backdrop exact, translucent within 1). It reads the workspace `Cargo.lock` and asserts `netrender`, `netrender_device`, `paint_list_api` and `paint_list_render` resolve to a single revision (`d92050146768357ead4e4e42967866be7061262e` here). Rulings by Mark's card round, 2026-10-20.

Release run on O-PC (RTX 4060 Laptop, Vulkan, Rust 1.99.1): **16 checks pass, 1 fails**. Opaque, translucent (`[127,128,0,255]`), removal and frame composition (parent and child both owning image key 1) are correct. **Replacement fails:** after the same URL's pixels change from 16x16 blue to 8x8 magenta, the GPU draws the 8x8 size in the old blue. The paint list holds the new pixels; a fresh surface key draws the same stale blue, so the cache is renderer-wide. `CpuImageCache::refresh` in NetRender `d92050146` keeps an entry per `ImageKey` ("immutable pixels until absent") while Livery reuses per-list ordinal keys across frames; its dimension `debug_assert` is compiled out in release. Whether Livery must key by content/generation or NetRender must compare blob identity is open (Mark's fork). Receipt, five readback PNGs and the run excerpt: [`receipts/2026-10-20_img_gpu.json`](receipts/2026-10-20_img_gpu.json). The existing `Arc::ptr_eq` retention witnesses never reached the renderer, which is why they did not catch this.
